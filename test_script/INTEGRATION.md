## 0. 요약

연동 가능하다. `--fail-rate 0.25`(스텝당 25% 확률로 주행 실패/드리프트)에서도 1열·2열·3열 전부

다만 **설계 문서 원안 그대로 구현하면 네 군데에서 확정적으로 멈추거나 충돌한다.**
시뮬레이터는 전부 고쳐 놓았고, 아래 §2 에 무엇을 왜 바꿨는지 적었다. 연동 코드는 시뮬레이터 쪽을 따라야 한다.

| # | 원안 | 증상 |
|---|---|---|
| §2.1 | 현재 위치를 `t=0,1` 예약 | 마주친 두 대가 영구 정지. `stuck` 플래그도 안 뜸 |
| §2.2 | 충돌 시 우선순위 낮은 쪽 대기 | 1열 복도에서 **두 로봇이 서로를 관통** |

## 2. 설계 문서에서 바꾼 것 — 안 바꾸면 멈춘다

### 2.1 현재 위치 예약은 `t=0` 만 (문서 §3.4 는 `t=0,1`)

문서는 모든 로봇의 현재 위치를 `t=0` 과 `t=1` 에 예약하라고 한다. **이러면 라이브락이 생긴다.**

1열 복도에서 마주 보는 H(상위)/L(하위):
- L 은 `t=1` 에 제자리 대기가 **항상 합법**이다(자기 예약은 `release_all` 로 풀리므로). 후퇴는 목표에서 멀어져
  `h` 가 커지므로, A\* 는 후퇴를 `t=2` 이후로 미루는 쪽의 `f` 가 낮다고 판단한다.
- H 는 L 의 `t=1` 예약에 막혀 역시 `t=1` 에 대기한다.
- 실행은 `plan[1]`(= `t=1`) **한 칸만** 한다. 둘 다 영원히 안 움직인다.

실측: 1열 복도, t=167 부터 두 대가 인접한 채 영구 정지. 계획서 상으로는 둘 다 "정상 경로"를 갖고 있어
`stuck` 플래그도 안 뜬다. 즉 **로그만 봐서는 원인을 못 찾는 종류의 정지**다.

`t=0` 만 예약하면 H 가 `t=1` 에 L 의 칸을 예약하고, L 은 `t=1` 에 강제로 비켜난다.
barrier 동기에서는 모든 로봇이 한 스텝을 동시에 실행하므로, H 가 L 이 비우는 칸으로 같은 스텝에
따라 들어가는 것은 정상이다(같은 방향 복도 추종과 동일한 상황).

> **연동 시 주의**: 이 "따라 들어가기"는 barrier 가 **모든 로봇의 도착을 기다린다**는 전제에 의존한다.
> barrier 를 느슨하게 하거나(예: 타임아웃으로 일부만 진행) ADG 비동기로 바꾸면 이 전제가 깨진다.
> 그때는 `t=1` 예약을 되살리는 대신 ADG 의존 간선으로 순서를 강제해야 한다.

### 2.2 실행 안전망은 "이미 그 칸에 서 있는 로봇이 우선"

문서 §3.4 의 "충돌이면 그 로봇은 대기"를 우선순위 순으로 순진하게 구현하면 **로봇이 서로를 통과한다.**

하위 로봇 L 이 `stuck` 이라 제자리에 있는데 상위 로봇 H 가 그 칸으로 들어오는 경우:
- 우선순위 순 처리 → H 가 먼저 그 칸을 차지
- L 은 "충돌이니 대기" → 그런데 L 의 대기 위치가 **바로 그 칸**
- 둘 다 같은 칸. 다음 스텝에 각자 반대편으로 빠져나가 **1열 복도에서 서로를 관통**

실측: 1열 복도 정면, t=9. 실제 로봇이면 정면 충돌이다.

올바른 판정은 "그 칸에 **이미 서 있는** 로봇이 유지하고, 들어오려던 쪽이 제자리로 되돌아간다"이다.
되돌림이 뒤 로봇에 연쇄되므로 고정점까지 반복해야 한다. `lane_sim.execute()` 의 해당 블록을 그대로 옮길 것.

**연동에서 이 안전망은 시뮬보다 더 중요하다.** amcl 스냅 오차·주행 실패로 계획과 실제가 어긋난 상태에서
매 스텝 마지막 방어선이 된다.

### 2.3 휴리스틱은 체비셰프가 아니라 BFS 거리표 (문서 §3.3)

문서는 "목표까지 체비셰프 거리"를 쓰라고 한다. **윈도우 절단(`t==W`)과 만나면 교착한다.**

복도처럼 벽을 우회해야 하는 구간에서는 전진해도 체비셰프 값이 안 줄어든다
(예: 목표가 `(28,0)`, 로봇이 `(17,11)` → 오른쪽으로 8칸 가도 `max(dx,dy)` 는 11 그대로).
그러면 "8스텝 대기"와 "8스텝 전진"의 `f` 가 같아지고, 동점 처리에 따라 대기가 안정 고정점이 된다.

실측: 1열 복도, t=40 부터 로봇 한 대가 **빈 복도에서** 아무 이유 없이 영구 정지.

`dist_field()` — 목표에서 8방향 BFS로 편 거리표 — 를 쓰면 전진할 때 `f` 가 반드시 줄어 이 고정점이 사라진다.
이동 최소 비용이 1.0 이므로 admissible 하다. HCA\* 원논문의 RRA\* 와 같은 역할이다.

**연동 시**: 거리표는 목표가 바뀔 때만 다시 계산한다(`Robot.hgoal` 캐시). 정적 맵 기준이므로
동적 장애물은 반영하지 않는다 — 그건 Nav2 로컬 costmap 담당이다.

### 2.4 상태에 heading 을 넣고 회전 비용을 매긴다 (문서에 없음)

문서 상태는 `(x, y, t)` 라 **회전 비용이 0**이다. 격자에서는 8방향이 전부 대칭이지만 실제로는 아니다:

| 격자 이동 | 실제 |
|---|---|
| 앞 칸 | 직진 |
| 옆 칸 | 90° 제자리 회전 + 직진 |
| 뒤 칸 | 180° 회전(1열 복도에선 불가) 또는 후진 |
| 대각 | 45° 회전 + 1.41배 거리 |

비용이 전부 1이면 A\* 는 동점을 대량으로 만들고, 실행이 비싼 지그재그 경로를 태연히 낸다.
barrier 동기라 한 대의 회전이 **전체를 멈춰 세운다.**

상태를 `(x, y, heading, t)` 로 올리고 회전량에 비용을 매긴다. 상태 수는 40×16×8×9 ≈ 46k, 여전히 밀리초다.
예약 테이블은 셀 단위 그대로라 안 건드린다.

```python
BASE_COST = (1.0, 1.4)                    # (직교, 대각)
TURN_COST = (0.0, 0.4, 1.0, 1.5, 2.0)     # 0 / 45 / 90 / 135 / 180 도
WAIT_COST = 1.0
```

> **연동 시 반드시 재보정할 것.** 위 값은 `max_vel_theta 0.5 rad/s`, `max_vel_x 0.5 m/s`, 셀 2.2 m 기준의 어림값이다.
> 실제로는 **한 칸 직진에 걸린 시간 / 90도 제자리 회전에 걸린 시간**을 스톱워치로 재서
> `TURN_COST[2] = (회전시간 / 직진시간)` 으로 맞추는 것이 정확하다. barrier 동기에서는 이 비율이
> 그대로 전체 처리량에 반영된다.
>
> 측정 전이라도 `TURN_COST` 를 전부 0 으로 두지는 말 것. 0 이면 §2.4 의 지그재그가 그대로 돌아온다.

### 2.5 stuck 인 로봇을 계획 순서 맨 앞으로 (문서 §3.1 은 `(-urgency, id)` 고정)

문서대로 우선순위를 긴급도 고정으로 두면 **1열 복도에서 영구 교착한다** (실측: 시드 10개 중 6개).

교착 배치 — 1열 복도에 세 대:

```
R1(u2, 목표 오른쪽)   R3(u1, 목표 오른쪽)   R2(u3, 목표 왼쪽)
     x=15                 x=16                  x=23
```

1. R2(최상위)가 먼저 계획해 `t=7` 에 R1 의 칸까지 예약한다.
2. R1 은 "t=7 까지만 비우면 된다"고 판단해 `t=1..6` 은 **제자리를 예약**한다.
   목표가 오른쪽이라 미루는 쪽의 `f` 가 낮다. A\* 로서는 최적이다.
3. R3 는 왼쪽(R1 의 칸)이 `t=0..7` 예약돼 있어 후퇴 불가, 오른쪽은 R2 → 경로 없음(`stuck`).
4. 그런데 실행은 `plan[1]` 한 칸뿐이다. **R1 은 영원히 `t=7` 에 도달하지 못한다.**

§2.1 과 같은 계열이다: *계획에는 강제 이동이 들어 있는데 그게 항상 `t≥2` 라 실행되지 않는다.*

**연속 대기 시간으로 긴급도를 올리는 방식(`wait_cnt // N`)은 듣지 않는다.**
끼인 세 대가 같이 대기하므로 보정이 균등하게 올라가 상대 순서가 그대로다 (실측: 시드 3, t=180~189).

`stuck` 인 로봇을 맨 앞으로 보내면 된다:

```python
def _prio(r):
    return (0 if r.stuck else 1, -r.urgency, r.id)
```

그 로봇이 거의 빈 예약 테이블에서 먼저 방향을 잡고, 막고 있던 로봇이 그 예약에 밀려
**`t=1` 에 실제로** 비켜난다. `stuck` 은 `plan_step` 이 매번 갱신하므로 풀리는 즉시 원래 우선순위로 돌아온다.
(PIBT 의 우선순위 상속)

> **연동 시 의미**: 교착 중에는 저긴급도 로봇이 고긴급도보다 먼저 계획된다.
> 긴급도가 "응급 상황 대응" 같은 **절대 규칙**이어야 한다면 이 방식은 못 쓴다.
> 그 경우 1열 복도를 "한 번에 한 방향"으로 잠그는 방식으로 가야 하는데,
> 실제 맵의 모든 1열 복도를 셀 단위로 손수 표시해야 하고(= `corr_of` 가 필수가 된다)
> 처리량이 떨어지며, 기아 방지를 위해 결국 대기 시간 기반 양보 규칙이 다시 필요해진다.

### 2.6 복도 간격 K (문서 §3.3 조건 5) — 기본값 1

문서는 K=2 를 제안하지만, 시뮬 결과 **K=1/2/3 의 차이가 측정되지 않는다**
(1열 정면 해소 42스텝으로 동일, 300스텝 도착 횟수 동일).

이유:
- K=1 은 조건 3(vertex)이 이미 공짜로 보장한다. 조건 5 의 실질 내용은 K≥2 일 때만 생긴다.
- 간격 2 가 격자상으로 더 안전한 건 없다. 이 규칙은 **연속 공간의 몸통 크기를 이산 격자에서 흉내 내는 대용품**인데,
  그 여유는 이미 셀 크기(≥ 회전 지름, §3)에 들어가 있다. 이중 계산이다.
- 문서 문구대로 "진행 방향 앞 1..K칸"을 마주 오는 로봇에게도 적용하면 §3.5 의 후진 회피를 방해한다.
  시뮬레이터는 **같은 방향에만** 적용하도록 제한했다.
- barrier 동기 하에서는 추종자가 선행자에게 물리적으로 붙을 수 없다. 한 스텝에 한 칸씩만 목표를 받고,
  추종자가 이동 명령을 받는 시점엔 선행자가 이미 그 칸을 비운 뒤다.

실측: K=1/2/3 의 1열 정면 해소가 42스텝으로 **동일**하고 도착 횟수도 차이가 없다.
오히려 K=2 로 올리면 간격 위반이 수백 건 잡힌다 — 규칙이 전이 제약일 뿐 불변식이 아니라서다.

**연동 후에도 K=1 로 시작할 것.** 추종 거리는 Nav2 로컬 costmap 의 inflation 이 잡는다.
K 를 올려야 할 상황("선행자가 셀 중간에서 멈춤")은 K 로 안 풀리고 §6 의 재스냅으로 풀어야 한다.

조건 5 는 전이 제약이지 불변식이 아니다 — 선행자가 방향을 틀면 간격 K 는 깨질 수 있다.
그래서 `--check` 는 이걸 assert 가 아니라 **위반 횟수 지표**로만 센다. 연동 코드에서도 assert 로 걸지 말 것.

## 3. 셀 크기 — 먼저 정해야 하는 것

로봇이 셀 안에서 제자리 회전할 수 있어야 한다. `(x, y, heading, t)` 상태가 90°/180° 회전을
한 칸 안에서 일어나는 일로 취급하기 때문이다.

```
셀 한 변 ≥ 로봇 대각 길이 = sqrt(길이² + 폭²)
```

| 복도 열 수 | 필요 실제 폭 |
|---|---|
| 1열 | ≥ 셀 1개 |
| 2열 | ≥ 셀 2개 |
| 3열 | ≥ 셀 3개 |

**셀 크기가 이 조건을 못 지키면 회전 비용 모델 전체가 무효**가 되고, 격자상 합법인 이동이 실제로는
실행 불가가 된다. 그 경우 대각선 이동을 금지하고(`DIRS` 를 4방향으로) 셀 크기를 다시 잡는 편이 낫다.

복도 폭은 맵 PNG 에 거리변환을 걸어 재는 것이 rviz `Measure` 보다 빠르고 정확하다:

```python
import numpy as np; from PIL import Image
from scipy.ndimage import distance_transform_edt as edt
a = np.array(Image.open('MAP.png').convert('L'))
free = a >= int(255 * (1 - 0.196))          # map yaml 의 free_thresh
width = edt(free) * 0.05 * 2                # * resolution * 2 = 통과 가능 폭(m)
print(np.percentile(width[free], [50, 75, 90]))
```

## 4. 격자 생성

`make_map()` 을 Nav2 맵 yaml 다운샘플로 교체한다.

```
셀 (cx, cy) 안에 점유 픽셀이 하나라도 있으면 OBST, 아니면 FREE
셀 중심 실좌표 = origin + (cx + 0.5, cy + 0.5) * cell_m
```

`corr_of` 는 좁은 구간을 손으로 지정한다. 자동 검출은 필요 없다 — 조건 5 가 기본값 K=1 로
사실상 꺼져 있으므로 `corr_of` 는 빈 dict 여도 알고리즘이 돈다.

> **더 게으른 방법**: 맵이 하나로 고정이고 격자가 작으면(수백 셀) 다운샘플 스크립트를 만들지 말고
> 격자를 상수로 하드코딩하는 편이 유지비가 싸다. 맵을 자주 바꿀 때만 스크립트를 쓴다.

**셀 격자와 Nav2 costmap 은 별개다.** 격자는 정적 장애물만 안다. 사람·박스 같은 동적 장애물은
격자에 넣지 말고 Nav2 로컬 costmap 에 맡긴다. 격자에 넣으면 매 스텝 격자가 바뀌어
거리표 캐시(§2.3)가 무의미해지고 계획이 진동한다.

---

## 5. 실행 — barrier 동기

```
매 스텝:
  1. /carterN/amcl_pose 구독 -> 가장 가까운 셀로 스냅 -> r.pos
  2. r.pos == r.goal 인 로봇에 새 목표 배정
  3. plan_step(robots, grid, corr_of, W, K)      # 시뮬과 동일
  4. §2.2 안전망 적용 -> 각 로봇의 확정 다음 셀
  5. 셀 중심 좌표로 목표 전송 (§5.1)
  6. 전원이 배정 셀에 들어올 때까지 대기 (barrier)  -> 스텝 +1
```

문서 §5.1 그대로다. **격자 시간 `t` 는 실제 시간과 무관하다.** 예약 테이블은 시각이 아니라
순서만 보장하면 되므로, Nav2 가 얼마나 느리게 주행하든 예약이 깨지지 않는다.
대가는 "가장 느린 로봇에 전체가 맞춰짐"이다. 3대면 감수한다.

### 5.1 다음 셀로 보내는 방법

`plan[1]` 이 **현재 heading 기준 뒤쪽**이면 후진, 아니면 전진이다.

- **전진**: `NavigateToPose` 로 셀 중심 + 이동 방향 heading. 문서의 `NavigateThroughPoses` 는
  셀을 하나만 보내므로 불필요하다.
- **후진**: `behavior_server` 의 `nav2_behaviors::BackUp` 액션을 거리 지정해 직접 호출한다.
  params 수정 0줄, Nav2 우회 코드 0줄이다.

  문서 §5.4 의 1번 안(`min_vel_x: -0.2`)은 **거의 확실히 실패한다(미검증, 근거만 제시)**:
  global planner(NavFn)가 후진 경로를 만들지 않으므로 DWB 가 따라갈 path 자체가 "돌아서 가라"로 나오고,
  `PathDist` / `GoalDist` / `PathAlign` critic 이 전부 그 전진 path 를 향해 점수를 준다.
  `min_vel_x` 만 음수로 바꿔도 후진 궤적이 선택될 이유가 없다.

  §2.4 의 회전 비용 덕분에 180° 기동은 **계획 단계에서 이미 억제**된다(실측: 스텝·로봇당 0.007~0.05회).
  즉 후진은 드물게만 필요하다.

### 5.2 도착 판정은 Nav2 액션 결과가 아니라 amcl_pose 로

`xy_goal_tolerance` 가 0.1 m 면 셀 중심에 10 cm 이내로 **정지**해야 액션이 성공한다.
셀 2.2 m 에서 10 cm 정밀도는 과하고, DWB 가 `RotateToGoal` 로 최종 정렬하는 데 스텝마다 수 초를 쓴다.
barrier 동기라 그 시간이 전체에 곱해진다.

대신 coordinator 가 `amcl_pose` 로 **"셀 반경(예: `cell_m * 0.4`) 안에 들어옴"** 을 판정하고
바로 다음 목표를 덮어쓴다. 로봇은 감속하지 않고 다음 셀로 이어 간다.

## 6. 실패 복구 — 연동의 핵심

barrier 는 "전원 도착"을 기다리므로, **한 대라도 도착에 실패하면 전체가 영원히 멈춘다.**
Nav2 abort, DWB 진동, 사람이 앞을 막음 — 전부 정상적으로 일어난다.
저장소에 사람 에셋이 있는 걸 보면 이건 예외가 아니라 상시 상황이다.

```
barrier 타임아웃 (예: 예상 주행 시간 × 3)
  -> 해당 로봇 goal 취소
  -> amcl_pose 를 가장 가까운 셀로 재스냅
  -> plan_step 재호출
```

재스냅하면 **두 로봇이 같은 셀로 스냅될 수 있다.** 문서 §3.4 는 이 상태를 가정하지 않는다
(`table.reserve(r.pos, t=0, r.id)` 에서 뒤 로봇이 앞 로봇 예약을 덮어쓴다).

`lane_sim.plan_step` 은 이걸 처리한다: 예약을 우선순위 순 `setdefault` 로 넣어
**긴급도 높은 쪽이 셀을 소유**하고, 낮은 쪽은 `t=0` 예약 없이 탈출 경로를 찾는다(`r.displaced`).

이 경로가 실제로 도는지는 `--fail-rate` 로 검증한다:

```bash
python3 test_script/lane_sim.py --check              # fail_rate 0.1 / 0.25 포함
python3 test_script/lane_sim.py --fail-rate 0.2      # GUI 로 육안 확인
```

`--check` 는 겹침이 **3스텝 안에 풀리는지**를 assert 한다. 연동 코드를 고친 뒤에도 이 검증을 먼저 돌릴 것.

### 6.1 시드 하나로 검증하지 말 것

시드 1 만 쓰면 1열 케이스가 통과한다. 시드 10개로 넓히면 **6개에서 영구 교착이 나왔다**(§2.5).
`--check` 는 기본 5개 시드를 쓰고 `--seeds` 로 늘릴 수 있다. 연동 코드를 고친 뒤에는
`--seeds 10 --steps 500` 으로 돌릴 것.

## 7. 환경 쪽 확인 사항

- coordinator 노드도 `use_sim_time: True`. 안 하면 §6 의 barrier 타임아웃이 wall clock 으로 돌아
  Isaac 이 느릴 때 멀쩡한 로봇을 실패로 판정한다.
- coordinator / Nav2 / Isaac 이 같은 RMW 를 쓰는지 확인. `~/.bashrc` 에 cyclonedds 설정 후
  fastrtps 로 덮어쓰는 줄이 있어 혼동하기 쉽다.
- AMCL 초기 위치가 3대 모두 주어지는지 확인. 안 주면 첫 셀 스냅부터 틀린다.
- 다중 로봇 launch 가 쓰는 params 파일이 단일 로봇용 튜닝 파일과 **다르다**.
  footprint / 속도 / inflation 이 서로 다르므로 §3 의 셀 크기를 정하기 전에 어느 쪽을 쓸지 먼저 정할 것.

## 8. 한계선

- 로봇 8~10대로 늘거나 우회 공간이 좁아지면 `stuck` 이 빈발한다. 그때는 전역 MAPF(CBS) 또는 RMF.
- barrier 는 전체를 가장 느린 로봇에 맞춘다. 답답하면 ADG 비동기 — 단 §2.1 의 주의사항을 볼 것.
- 격자는 정적 맵만 안다. 동적 장애물이 **복도를 통째로 막으면** 격자는 그 사실을 모르고
  계속 그 복도로 계획한다. barrier 타임아웃 → 재스냅 → 같은 계획 반복이 된다.
  그 상황이 실제로 생기면 "타임아웃 N회 연속인 셀을 일시적으로 OBST 처리" 를 추가해야 한다(미구현).
